## Sprint 1 — Data Foundation

**Goal:** Establish the complete relational backbone — all 6 master tables (Supplier, Staff, Dealer, Grade, Trading Size-Design, Design-Grade map) with CRUD admin screens, soft-delete via `is_active`, seed data per the sample PRD, PostgreSQL schema, and Alembic baseline migration — so every subsequent sprint has a stable schema to build on.

**Features:** F-001 Supplier · F-002 Staff · F-003 Dealer · F-004 Grade · F-005 Trading Size-Design · F-006 Design-Grade Combination Table
**Modules:** M-001 (Master Data) · M-007 (Persistence & Migrations)
**Dependencies:** None

### What gets built
| Module | Deliverable |
|---|---|
| M-007 | SQLAlchemy 2.x models for all 6 master tables + 6 transaction tables + 1 stock_ledger; Alembic baseline migration; seed scripts for grades (9), suppliers (3), dealers (3), staff (9), designs (3), design-grade combinations (6). FastAPI app skeleton, Docker compose with PostgreSQL 16. |
| M-001 | REST CRUD for all 6 masters with soft-delete. `/designs/{id}/grades` endpoint returning only active mappings. Next.js admin pages for each master. |

### Sprint 1 Acceptance Gate
- All 13 tables exist in PostgreSQL with correct columns, FKs, and UNIQUE constraints
- Admin can Create / Read / Update / Soft-delete every master
- Soft-deleted records do not appear in their respective form dropdowns
- All seed data loads via a single `alembic upgrade head && python scripts/seed_master_data.py` flow
- `GET /designs/{id}/grades` returns the correct active-grade list for every seeded design
- Full stack runs via `docker-compose up` and admin pages are reachable on `http://localhost:3000`

## Sprint 2 — Transaction Forms + Stock Ledger

**Goal:** Deliver all 3 transactional forms (Inward, Sales, Adjustment) with grade-row auto-population, atomic header+lines+ledger writes inside a single DB transaction, and `SELECT FOR UPDATE` row-level locking on the stock ledger per (design_id, grade_id) to handle concurrent saves correctly.

**Features:** F-007 Inward · F-008 Sales · F-009 Adjustment
**Modules:** M-002 (Transaction Forms) · M-003 (Stock Ledger)
**Dependencies:** S1

### What gets built
| Module | Deliverable |
|---|---|
| M-003 | Domain functions `apply_inward / apply_sale / apply_adjustment / closing_balance / opening_balance`. `tbl_stock_ledger` running-balance writes with SELECT FOR UPDATE serialization. Back-dated transaction recomputes running balance forward within same DB txn. |
| M-002 | `POST /inward`, `POST /sales`, `POST /adjustments` — each runs header + lines + ledger updates atomically. Date-bound validation (today / today-7d). RULE-005, RULE-006, RULE-015, RULE-017 enforced server-side. ERR-001..ERR-012 codes returned. `GET /designs/{id}/grades-with-cb?stock_date=…` for the Adjustment form. Next.js Inward / Sales / Adjustment form pages with reactive grade-row rendering. |

### Build order within sprint
1. M-003 stock ledger domain functions + tests
2. M-002 POST /inward + Inward UI
3. M-002 POST /sales + Sales UI
4. M-002 `grades-with-cb` endpoint + POST /adjustments + Adjustment UI

### Sprint 2 Acceptance Gate
- Inward, Sales, and Adjustment forms save end-to-end against a real PostgreSQL
- Selecting a design renders exactly the active grade rows for that design
- Date bounds enforced server-side (ERR-001 / ERR-002)
- NOS validation rejects ≤ 0 and non-integers (ERR-007)
- Blank/zero NOS rows silently skipped (RULE-017)
- Stock ledger row count and running balance update correctly after each form save
- Concurrent inward saves on the same (design, grade) serialize via SELECT FOR UPDATE (integration test simulates two simultaneous POSTs)
- Adjustment form pre-fills software CB per grade and applies differences correctly

## Sprint 3 — Dashboard, Sales Report, Carry-Forward

**Goal:** Complete the read-side of the system. Stock Dashboard returns Opening/Inward/Outward/Adjust/Closing per active (design, grade) as of any selected date. Sales Report renders Consolidation + Transaction views simultaneously with multi-select optional filters. Monthly carry-forward verified end-to-end including back-dated transactions crossing month boundaries.

**Features:** F-010 Dashboard · F-011 Sales Report · F-012 Monthly Carry-Forward
**Modules:** M-004 (Dashboard) · M-005 (Sales Reporting)
**Dependencies:** S1, S2

### What gets built
| Module | Deliverable |
|---|---|
| M-004 | `GET /dashboard?as_of_date=YYYY-MM-DD`. Reads `tbl_stock_ledger` for the latest row per (design, grade) where `txn_date <= as_of_date`. Reads `tbl_inward_lines`, `tbl_sales_lines`, `tbl_adjustment_lines` for month-to-date sums. Next.js Dashboard page with date picker. |
| M-005 | `GET /reports/sales?…` returning `{consolidation[], transactions[]}` payload. Multi-select filter parsing for date_from/date_to/dealer_ids/places/design_ids. Next.js Sales Report page with dual-pane layout (Consolidation above Transaction, both visible always). |
| M-003 (carry-fwd) | Carry-forward logic explicitly tested: AC-051 (Month N+1 opening = Month N closing), AC-052 (no prior data → 0), AC-053 (back-dated txn straddling month boundary remains correct). |

### Sprint 3 Acceptance Gate
- Dashboard returns sub-second response for any single date with seeded multi-month data
- Dashboard rows match the LLD example calculations exactly
- Sales Report filters work in any combination including no-filter (full dataset)
- Consolidation totals always equal SUM of Transaction rows for the same filter set (AC-050)
- Both Consolidation and Transaction render simultaneously — no toggle, no tab
- Month-end carry-forward: first transaction on Jul-01 sees Opening = Jun-30 Closing; integration test verifies a back-dated Jun-28 sale modifies June's closing AND July's opening together
- All 53 acceptance criteria from the PRD have a passing integration or unit test
