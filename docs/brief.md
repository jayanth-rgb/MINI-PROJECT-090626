## Product

**Name:** Jayanth Trading Tiles System

**Objective:** A dedicated trading-tiles module that lets a single tile trading business record inward purchases from suppliers, outward sales to dealers, physical stock adjustments, and view current stock position and sales reports — all organised by tile design and grade.

### Users
- **Data Entry Staff** — records daily inward, sales, and adjustment entries
- **Stock Verifier** — physically counts tiles at the warehouse and provides the count for adjustments
- **Management / Supervisor** — views the stock dashboard and runs sales reports

### Core Features
1. Master data: Supplier, Staff, Dealer, Grade (9 grades: 1, 2, 2A, 4, 5, 6, 1OB, OB, DIM), Trading Size-Design, Tile Design-Grade combination table
2. Trading Tiles Inward Form — grade rows auto-populated per selected design
3. Trading Tiles Sales Form — grade rows auto-populated per selected design
4. Trading Tiles Adjustment Form — physical vs software CB difference per grade
5. Stock Dashboard — Opening / Inward / Outward / Adjust / Closing per design-grade, filtered by date
6. Sales Report — Consolidation + Transaction views shown together with multi-select filters
7. Monthly stock carry-forward (closing balance of Month N → opening of Month N+1)

### Non-Goals (V1)
- User login and access control (deferred to V2)
- Pricing, invoicing, or payment tracking
- Manufacturing tiles module
- Inward Report (only Sales Report in this version)
- Report export to PDF or Excel

### Success Criteria
- Closing balance matches physical count after every adjustment entry
- Only valid design-grade combinations appear on forms (RULE-005 / RULE-006)
- Sales Report Consolidation totals always equal SUM of Transaction Report lines for the same filters
- Each data entry completes within 2-3 minutes
- Dashboard reflects all transactions up to any selected date
- Opening balance auto-populates at month start with no manual intervention

## Engineering

| Frontend | Next.js 15 (React 19 + TypeScript, App Router) |
| Database | PostgreSQL 16 |
| Infra | Docker + docker-compose (local), portable to any cloud |

### Integrations
None — fully self-contained single-tenant system in V1.

### Performance Constraints
- Single-factory workload — single-digit concurrent users
- Sales Report Transaction view may need pagination beyond ~1000 rows (LLD open item #7)
- Stock ledger reads back the materialised running balance — dashboard should be sub-second for any single date

### Deployment Context
Docker images for backend and frontend, PostgreSQL via docker-compose for local dev, portable to any cloud container runtime.

### Data Shape
Relational. 6 master tables, 6 transaction tables (3 header + 3 line), 1 stock ledger materialised table. Most operations are header + line-items in a single transaction.

## Constraints
- Transaction dates restricted to today and up to 7 days prior — no future dates (RULE-001, RULE-002)
- Adjustment Form: only one tile design per entry
- Trading Size-Design Master is separate from any manufactured-tile design list
- No user authentication in V1 — all users share full access
- Grade rows on Inward / Sales forms must derive from Tile Design-Grade Table, not hardcoded

## Risks
- **Stock ledger concurrency** — simultaneous saves on the same Design+Grade need row-level locking (LLD open item #5)
- **Dashboard performance** — live SUM over inward / sales / adjust per design-grade may need a materialised running-balance table (LLD open item #3)
- **Month-end carry-forward** correctness depends on a deterministic "last day of previous month" calculation across timezones — DB stored in UTC, dates handled as plain DATE

## Sprint 1 Hypothesis
Sprint 1 delivers the **data foundation**: all 6 master tables (Supplier, Staff, Dealer, Grade, Trading Size-Design, Design-Grade map) with CRUD admin screens, soft-delete (`is_active`), seed data per the sample PRD, and PostgreSQL schema + Alembic baseline migration. No transaction forms or stock ledger yet — those land in S2 and S3.
